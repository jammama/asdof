# 자동 예약 기능 — jointips 회의실 예약 봇 (Go) 구현 명세

> 이 문서는 **단독 구현 명세서**다. 다른 코드/문서 참조 없이 이 문서만으로 구현할 수 있도록
> 대상 사이트의 HTTP 프로토콜, 필드 값, 함정, 알고리즘, 설정, 검증 절차를 모두 포함한다.
>
> 문서 내 프로토콜 정보는 실제 사이트 응답과 저장된 페이지 스냅샷을 분석해 확인한 것이다.
> 확인 수준을 아래처럼 표기했으니 신뢰도를 판단할 때 참고할 것.
>
> - **[확인]** — 실제 응답 또는 페이지 소스에서 직접 확인한 사실.
> - **[미확인]** — 로그인 자격증명이 필요해 확인하지 못함. 런타임에 실측 후 확정해야 하는 부분.

---

## 1. 목표

매일 정해진 시각(기본 12:00:00.05)에 자동으로 실행되어, 미리 지정해 둔 **회의실 + 시간대**로
jointips 회의실 예약을 신청하고, 결과를 **Notion 데이터베이스에 기록**한다.

- 사용자의 개인 서버(메모리 1GB)에서 cron으로 구동한다.
- **브라우저(Chromium/Playwright)를 쓰지 않는다.** 순수 HTTP 클라이언트로 구현한다.
  대상 사이트는 CSRF 토큰·캡차·JS 계산 서명이 없는 평범한 PHP(그누보드 5.x) 폼 기반이라
  HTTP만으로 완전히 재현 가능하다. **[확인]**
- 알림 채널(텔레그램/Slack 등)은 만들지 않는다. **결과 기록은 Notion DB 한 곳에만** 남긴다.

### 왜 브라우저가 필요 없는지 (근거)

| 항목 | 확인 결과 |
|---|---|
| 서버 | `Server: Apache` — Cloudflare/WAF/봇 차단 없음 **[확인]** |
| 세션 | `Set-Cookie: PHPSESSID=...` 쿠키 하나 **[확인]** |
| CSRF 토큰 | 로그인 폼·예약 폼 모두 **없음** **[확인]** |
| 캡차 | 없음 **[확인]** |
| 예약 신청 | `<form method="post">` 일반 POST **[확인]** |
| 빈 슬롯 조회 | jQuery `$.ajax` POST → HTML 조각 반환 **[확인]** |
| 문자 인코딩 | UTF-8 (URL에 `%EC%9E%85%EC%A3%BC...` = "입주사전용") **[확인]** |

따라서 Go 표준 `net/http` + 쿠키 자 + HTML 파서만으로 충분하다. 예상 RSS 5~10MB.

## 2. 전체 동작 타임라인

`fire_at = 12:00:00.050`, `warmup_lead = 3m` 기준 예시.

```
11:57:00  cron 기동
          ├ 설정 로드 / 검증
          ├ 로그인 (POST /bbs/login_check.php) → PHPSESSID 확보
          ├ uid 풀 확보: 예약 페이지를 3~5회 GET 해서 uid 3~5개 수집
          ├ (옵션) 서버 시계 오차 점검: 응답 Date 헤더와 로컬 시각 비교
          ├ 멱등성 점검: Notion DB에 대상 날짜 기록이 이미 있으면 즉시 종료
          └ HTTP 커넥션 keep-alive 유지 (여기까지 TLS 핸드셰이크 완료)

11:59:59  sleep 종료 대기 (time.Timer)
12:00:00.050  ★ 1차 발사: 준비된 페이로드로 POST /bbs/write_update.php  (1 왕복)
          ├ 성공 판정 → Notion 기록 → 종료
          └ 실패 시 재시도 루프 진입
                 250ms 간격, 최대 15초 / 최대 40회
                 ├ 매 시도마다 uid 풀에서 새 uid 사용 (소진되면 페이지 재GET)
                 ├ 3회 연속 실패 시: 빈 슬롯 재조회 → 폴백 대상 재선정
                 └ 성공 또는 한도 도달 시 종료
12:00:15  종료. 결과를 로그 + Notion에 기록
```

## 3. 대상 사이트 프로토콜 명세

### 3.0 공통

- Base URL: `https://www.jointips.or.kr`
- 모든 POST는 `Content-Type: application/x-www-form-urlencoded`, UTF-8 퍼센트 인코딩.
  (예약 폼의 HTML은 `enctype="multipart/form-data"`지만 PHP는 urlencoded도 `$_POST`로 받는다.
  urlencoded가 더 짧고 빠르므로 이것을 쓴다. 만약 런타임에 거부되면 multipart로 전환. **[미확인]**)
- **쿠키 자를 반드시 사용**한다. `net/http/cookiejar` + `http.Client.Jar`.
  로그인 시 `PHPSESSID` 외에 방문자 식별용 쿠키가 하나 더 내려온다. 전부 보관·재전송한다. **[확인]**
- `User-Agent`는 일반 브라우저 문자열로 설정한다(기본 Go UA도 차단되지 않지만, 서버 로그상 자연스럽게).
- 리다이렉트: 그누보드는 302 대신 `<script>location.href=...</script>` 형태의 HTML을 반환하는
  경우가 있다. **HTTP 상태코드만으로 성공/실패를 판정하지 말 것.** (§3.6 참조)

### 3.1 로그인

```
POST /bbs/login_check.php
Content-Type: application/x-www-form-urlencoded

url=%2F&mb_id=<아이디>&mb_password=<비밀번호>
```

- 필드: `mb_id`, `mb_password`, `url`(로그인 후 이동 경로, 아무 값이나 무해), `auto_login`(선택, 생략 가능). **[확인]**
- 성공 판정: 응답 쿠키에 세션이 갱신되고, 이후 예약 페이지 GET 시 로그인 상태 콘텐츠가 나온다.
  **가장 확실한 판정은 §3.2의 예약 페이지를 GET 해서 `<input name="uid">`가 존재하는지 보는 것.**
  로그인 실패 시 예약 페이지는 로그인 폼으로 리다이렉트되므로 `uid`가 없다.
- 실패 시 즉시 중단하고 로그에 남긴다. **재시도 루프를 돌리지 말 것** (계정 잠금/불필요한 부하 방지).

### 3.2 예약 페이지 GET — `uid` 획득

```
GET /bbs/write.php?bo_table=campus_share_apply&wr_22=%EC%9E%85%EC%A3%BC%EC%82%AC%EC%A0%84%EC%9A%A9
```

- `wr_22`의 디코딩 값은 `입주사전용`이다. **[확인]**
- 응답 HTML에서 `<input type="hidden" name="uid" value="26052615100158">` 를 파싱한다. **[확인]**
- `uid`는 그누보드의 **중복 제출 방지 값**으로, 페이지를 로드할 때마다 새로 발급된다.
  형식은 타임스탬프 기반으로 보이지만(YYMMDDHHMMSS+2자리) **형식에 의존하지 말고 읽은 값을 그대로 전송**한다.
- **[중요] uid 풀 전략**: 재시도 루프에서 동일 `uid`를 재사용하면 중복 제출로 거부될 수 있다.
  워밍업 때 이 페이지를 3~5회 GET 해서 `uid`를 여러 개 모아두고, **재시도마다 새 uid를 사용**한다.
  풀이 소진되면 페이지를 다시 GET 해서 보충한다(1 왕복 추가 비용).

### 3.3 빈 슬롯 조회 (AJAX)

```
POST /ajax_common.php
Content-Type: application/x-www-form-urlencoded

std=location_select_new&wr_2=<빌딩코드>&wr_3=2026.08.25&wr_4=%ED%9A%8C%EC%9D%98%EA%B3%B5%EA%B0%84
```

- `std=location_select_new` 고정. **[확인]**
- `wr_2` = **빌딩 코드** (§4.1). 빈 문자열 `""`이면 전체 빌딩. **[확인]**
- `wr_3` = 대상 날짜, **`YYYY.MM.DD` 형식(점 구분)**. **[확인]**
- `wr_4` = `회의공간` 고정 (UTF-8 인코딩). **[확인]**
- 응답: `<tr>...</tr>` 반복으로 된 **HTML 조각**(테이블 body 내용만). 파싱 규칙은 §3.4.

### 3.4 조회 응답 파싱 규칙

응답은 회의실 1개당 `<tr>` 1개다.

```html
<tr data-wr8="41" data-wr6="3" data-wr7="25">
  <td>현승빌딩 4층</td>          <!-- 층 그룹의 첫 행에만 존재 (rowspan) -->
  <td>회의실 A</td>              <!-- 회의실 이름 -->
  <td></td>
  <td>4명</td>
  <td class="available tooltip2" data-time="09:00" idx="0" title="09:00" ...></td>
  <td class="available tooltip2" data-time="09:30" idx="1" title="09:30" ...></td>
  <td class="selected tooltip2"  data-time="10:00" idx="2"
      title="[앰버로드]앰버로드 과제회의" share_id="130785" ...></td>
  ... (총 24칸) ...
  <td class="selected" data-time="21:00" style="display:none;"></td>  <!-- 센티널 -->
</tr>
```

파싱 규칙:

1. **행 식별자**: `data-wr8` = 회의실 ID(예약 폼의 `wr_8`), `data-wr6` = 빌딩(`wr_6`), `data-wr7` = 층(`wr_7`). **[확인]**
2. **시간 셀**: `td[data-time]`. **09:00 ~ 20:30, 30분 단위 정확히 24칸** (`idx` 0~23), 시간 오름차순. **[확인]**
3. **가용 여부**: `class`에 `available` = 빈 슬롯, `selected` = 이미 예약됨. **[확인]**
4. **기예약 회의명**: `selected` 셀의 `title` 속성에 회의명이 들어있다(예: `[앰버로드]앰버로드 과제회의`).
   같은 예약은 `share_id`가 동일하다. **[확인]**
5. **[함정] 숨겨진 센티널 셀**: 각 행 끝에 `data-time="21:00"`, `class="selected"`,
   `style="display:none;"` 인 25번째 셀이 있다. **[확인]**
   - 이 셀은 **기예약 현황으로 취급하면 안 된다** (`display:none` 이거나 `title`/`share_id`가 없으면 제외).
   - 그러나 **20:30 슬롯의 종료시간(21:00)을 계산하는 데는 필요**하다. §3.5의 `wr_5` 규칙 참조.
6. **회의실 이름 추출**: 첫 `<td>`가 "빌딩"을 포함하면 그것이 `빌딩+층`이고 회의실명은 두 번째 `<td>`다.
   포함하지 않으면 첫 `<td>`가 회의실명이고, **빌딩+층은 같은 `data-wr7`을 가진 이전 행들을
   거슬러 올라가** 찾는다(rowspan 구조 때문). **[확인]**

### 3.5 예약 신청 POST ★핵심

```
POST /bbs/write_update.php
Content-Type: application/x-www-form-urlencoded
```

전체 필드 (예약 폼에서 추출한 실제 목록 **[확인]**):

| 필드 | 값 | 설명 |
|---|---|---|
| `uid` | §3.2에서 획득 | 중복 제출 방지값. 매 시도 새 값 |
| `w` | `` (빈 문자열) | 쓰기 모드 = 신규 |
| `bo_table` | `campus_share_apply` | 게시판 ID |
| `wr_id` | `0` | 신규 |
| `wr_1` | `T` | 고정 |
| `wr_2` | `회의실이용신청` | 고정 |
| `wr_3` | `2026.08.25` | **대상 날짜, 점 구분** |
| `wr_4` | `12:00` | **시작시간 (포함)** |
| `wr_5` | `16:00` | **종료시간 (배타적!)** — §아래 함정 |
| `wr_6` | `3` | 빌딩 코드 (조회 응답의 `data-wr6`) |
| `wr_7` | `25` | 층 코드 (`data-wr7`) |
| `wr_8` | `41` | **회의실 ID (`data-wr8`)** |
| `wr_15` | 연락처 | 예: `010-0000-0000` |
| `wr_17` | 담당자명 | |
| `wr_19` | `승인` | 고정 |
| `wr_22` | `입주사전용` | 고정 |
| `wr_subject` | 회의명 | |
| `wr_content` | `회의할 내용` | 고정(폼 기본값). 원하면 다른 텍스트도 가능 |
| `sca` `sfl` `stx` `spt` `sst` `sod` `page` | 모두 `` (빈 문자열) | 검색 상태 유지용. 빈 값으로 함께 전송 |

#### ★★ 최대 함정: `wr_5`는 배타적(exclusive) 종료시간

사이트 JS가 폼을 채우는 코드는 다음과 같다 **[확인]**:

```js
$("#share_wr_4").val($(".selection:first").attr("data-time"));       // = name="wr_4"
$("#share_wr_5").val($(".selection:last").next().attr("data-time")); // = name="wr_5"
```

`#share_wr_4` / `#share_wr_5`가 각각 `name="wr_4"` / `name="wr_5"` 입력이라는 것을 확인했다. **[확인]**
즉 `wr_5`에는 **마지막 선택 셀의 다음 셀 시각**이 들어간다.

> **12:00 ~ 16:00 (4시간, 8슬롯)을 예약하려면:**
> - 선택 슬롯: `12:00, 12:30, 13:00, 13:30, 14:00, 14:30, 15:00, 15:30` (8개)
> - `wr_4 = "12:00"`
> - `wr_5 = "16:00"`  ← 마지막 슬롯 15:30의 **다음** 칸
>
> 계산식: `wr_5 = wr_4 + (슬롯수 × 30분)`
>
> 이걸 틀리면 **매번 30분씩 짧게 예약된다.** 20:30 슬롯까지 잡는 경우 `wr_5 = "21:00"`이 되는데,
> 이 값이 존재하는 이유가 바로 §3.4의 숨겨진 센티널 셀이다.

### 3.6 성공/실패 판정

`write_update.php`의 응답 형태는 자격증명이 없어 확인하지 못했다. **[미확인]**
따라서 **응답에만 의존하지 말고 다음 3단 판정**을 구현한다.

1. **1차(빠름)**: 응답 본문에 `alert('...')` / `alert("...")` 패턴이 있으면 실패로 보고
   괄호 안 메시지를 추출해 로그에 남긴다. 그누보드는 오류를 이 방식으로 표시한다.
   (예상 메시지: 시간 겹침, 하루 2건 초과, 4시간 초과, 권한 없음 등)
2. **2차(확실)**: §3.3 조회를 다시 호출해서, 대상 `wr_8` 행의 `wr_4`~`wr_5` 구간 셀들이
   `available` → `selected` 로 바뀌었고 `title`에 우리 회의명이 들어있는지 확인한다.
   **이것이 성공의 최종 근거(ground truth)다.**
3. **3차(보조)**: 겹침 확인 API(§3.7)로 교차 검증.

**최초 실배포 전 반드시 §11의 검증 절차로 실제 응답을 한 번 관측하고, 그 결과로 1차 판정 로직을
확정할 것.**

### 3.7 겹침 확인 API (보조)

```
POST /ajax_common.php
std=dup_time&wr_3=2026.08.25&wr_4=12:00&wr_5=15:30&wr_8=41&wr_id=0
```

**[함정 2개]** **[확인]**

1. 이 API의 `wr_5`는 예약 폼과 **의미가 다르다.** 여기서는 **마지막 선택 슬롯의 시작시각(포함)**을
   넣는다. 위 예시에서 12:00~16:00 예약이면 `wr_5 = "15:30"`이다.
   (사이트 JS `CheckDupTime3`가 `$(".selection:last").attr("data-time")`을 그대로 쓴다.)
2. **응답 문자열 `"OK"` 는 "예약 불가"를 뜻한다.** 의미가 반전되어 있다.
   사이트 코드: `if (pStr == "OK") { alert("예약 불가합니다."); return false; }`
   → `"OK"` = 겹침 있음 = 실패. 그 외 값 = 겹침 없음.

이 API는 필수가 아니다(신청 전 사전 점검용). 발사 경로에서는 **왕복을 줄이기 위해 호출하지 않고**,
실패 원인 진단이나 성공 검증 보조로만 쓴다.

### 3.8 참고: 그 외 API (구현에 불필요, 오해 방지용으로 기록)

- `std=chk_office_day` — 팀의 당일 예약 건수 조회. 응답이 1보다 크면 사이트가 "팀 단위로 하루에
  2번만 예약 가능합니다" 경고를 띄운다. **[확인]**
- `std=chk_office_day_myteam_list` — 내 팀 예약 목록. 응답이 `목록HTML|건수` 형태이며, 건수가
  1보다 크면 사이트는 **화면에서 시간표를 숨긴다.** 그러나 이는 **표시만 가리는 것**이고
  `location_select_new` 응답 자체는 정상적으로 온다. 봇은 이 API를 무시하면 된다. **[확인]**
- `/bbs/ajax.filter.php` — 제목/내용 금칙어 검사. **클라이언트 측 UX용**이므로 봇은 호출하지 않는다. **[확인]**

### 3.9 사이트 정책 제약

- **7일 창**: 예약 가능 날짜는 `오늘 <= 날짜 < 오늘+7`이다. 페이지 렌더 시점에 서버가 이 경계를
  HTML에 상수로 박아 보낸다(스냅샷 예: 오늘 `2026-05-26`, 상한 `2026-06-02`). **[확인]**
  → **이 창은 자정에 롤링된다.** §6의 주의사항 참조.
- **하루 2건 / 최대 4시간(8슬롯)** 제한이 있다. 서버가 검증하므로 봇이 우회를 시도하지 않는다.
  설정 검증 단계에서 `duration_slots > 8`이면 즉시 에러로 중단한다.
- 재시도는 반드시 상한을 둔다(기본 15초/40회). 공용 서버이므로 과도한 요청을 보내지 않는다.

## 5. 슬롯 선택 알고리즘

### 5.0 설정 검증 (워밍업 단계)

1. `duration_slots`가 1~8 범위인지 확인. 아니면 즉시 에러 종료.
2. `start`가 30분 격자(`:00` 또는 `:30`)이고 `09:00`~`20:30` 범위인지 확인.
3. `start + duration_slots × 30분 <= 21:00` 인지 확인.
4. **조회를 1회 실행해 `room_id`(=`wr_8`)가 실제 응답에 존재하는지, 그리고 설정의
   `building`/`floor`가 해당 행의 `data-wr6`/`data-wr7`과 일치하는지 검증한다.**
   불일치하면 **조회 응답의 값을 신뢰**하고(설정을 덮어써서 사용) 경고 로그를 남긴다.
   — 사이트가 코드 체계를 바꿨을 때 조용히 오예약되는 것을 막기 위함이다.

> 워밍업의 이 조회는 발사 시각보다 몇 분 앞선다. 대상 날짜가 아직 7일 창을 벗어나 조회되지
> 않을 수 있다(§6 주의). 그 경우 검증은 **오늘 날짜로 조회**해서 회의실 코드 유효성만 확인한다.

### 5.1 1순위: 지정 대상 (기본 경로)

설정의 `targets` 배열을 **순서대로** 시도한다. 각 항목은 `room_id + start + duration_slots`로
완전히 확정된 예약이므로 **조회 없이 곧바로 POST**할 수 있다(1 왕복 = 가장 빠름).

발사 시점에는 첫 번째 대상으로 POST한다. 실패하면 재시도 루프에서 다음 대상으로 넘어간다.

### 5.2 2순위: 폴백 탐색 (`fallback.enabled = true`일 때)

지정 대상이 모두 실패하고 `fallback`이 켜져 있으면, 조회 결과에서 자동으로 자리를 찾는다.
아래는 기존 브라우저 확장에서 검증된 매칭 규칙이며 그대로 이식한다.

**후보 조건**

- 시작 셀은 `available`이고, `fallback.start` 이상 `fallback.start + start_window_minutes` 이하에서 시작.
- 시작 셀부터 **연속 `available`** 슬롯이 `min_slots` 이상이어야 한다.
- 길이는 `max_slots`(기본 8)까지만 취한다.

**우선순위**: ① 시작 시각이 빠른 것 → ② 동률이면 길이가 긴 것.

**3단계 탐색 순서**

1. `fallback.building` + `fallback.prefer_floor`에 해당하는 행들에서 탐색.
2. 실패하면 `fallback.building`의 **모든 층**에서 탐색.
3. `fallback.building`이 비어 있으면(전체) 모든 행에서 탐색.
4. 그래도 없으면 실패로 종료.

의사 코드:

```
func match(rows, targetMin, windowMin, minSlots, maxSlots) *Candidate {
    var best *Candidate
    for _, row := range rows {
        cells := row.TimeCells()          // 24칸, 시간 오름차순
        for i, c := range cells {
            if !c.Available { continue }
            startMin := toMinutes(c.Time)
            if startMin < targetMin { continue }
            if startMin > targetMin+windowMin { break }   // 시간순이므로 종료
            run := 0
            for j := i; j < len(cells) && run < maxSlots; j++ {
                if !cells[j].Available { break }
                run++
            }
            if run < minSlots { continue }
            cand := Candidate{Row: row, StartMin: startMin, Slots: run}
            if best == nil || cand.StartMin < best.StartMin ||
               (cand.StartMin == best.StartMin && cand.Slots > best.Slots) {
                best = &cand
            }
        }
    }
    return best
}
```

주의: 위 루프에서 `cells`는 **`display:none` 센티널을 제외한 24칸**이어야 한다.

## 6. 정밀 타이밍 설계

### 6.1 cron 등록

cron은 분 단위이므로 **cron은 기동 트리거로만** 쓰고 초 단위 정밀도는 프로그램 내부에서 맞춘다.

```cron
# 11:57에 기동 → 워밍업 후 프로그램이 12:00:00.050까지 대기
57 11 * * * /opt/jointips/bot -config /opt/jointips/config.yaml >> /var/log/jointips/cron.log 2>&1
```

systemd timer(`OnCalendar=11:57`, `AccuracySec=1s`)를 써도 동일하다. 어느 쪽이든 정밀 대기는
프로그램이 담당한다.

### 6.2 대기 및 발사

- 목표 시각은 **오늘 날짜 + `fire_at`** 을 로컬 타임존(`Asia/Seoul`)으로 계산한다.
- 대기는 `time.Sleep`/`time.Timer`로 하되, **목표 100ms 전에 깨어나 바쁜 대기(busy-wait) 없이
  짧은 슬립을 반복**해 오차를 줄인다. (`for time.Until(target) > 2*time.Millisecond { time.Sleep(500*time.Microsecond) }`)
- `fire_at`을 정각보다 **50ms 뒤로** 두는 것이 기본값이다. 서버 시계가 우리보다 몇 ms 느릴 때
  "아직 안 열림"으로 거부되는 것을 피한다.
- **NTP 필수**: 서버에 `chrony` 또는 `systemd-timesyncd`를 켜둘 것. 이것 없이는 전체 설계가 무의미하다.
- 워밍업 때 응답의 `Date` 헤더(초 단위)와 로컬 시각을 비교해 **1초 이상 오차가 나면 경고 로그**를
  남긴다. 초 단위 해상도라 미세 보정에는 쓸 수 없으니, 큰 오차 탐지용으로만 쓴다.

### 6.3 재시도 루프

```
attempt = 0
for time.Since(fireTime) < retry.max_duration && attempt < retry.max_attempts {
    result = submit(target, uidPool.Next())
    if result.Success { break }
    attempt++
    if attempt % 3 == 0 {
        // 3회 연속 실패 → 상황이 바뀐 것일 수 있으니 조회해서 대상 재선정
        target = reselect()   // §5.1 다음 대상 → 없으면 §5.2 폴백
    }
    sleep(retry.interval)
}
```

### 6.4 ⚠️ `fire_at` 시각에 대한 주의 (검증 필요)

사이트의 7일 창 검증 로직은 **페이지 렌더 시점에 `오늘 ~ 오늘+7일`로 계산**되어 HTML에 박힌다.
즉 **새 날짜가 열리는 경계는 자정(00:00)이지 정오(12:00)가 아닐 가능성이 높다.** **[확인: 창 계산 방식]**

사용자가 12:00:00을 지정한 이유가
(a) 조직 내 관행/경쟁 시간대이면 → `fire_at: "12:00:00.050"` 그대로 두면 된다.
(b) "새로 열리는 날짜를 선점"하려는 의도였다면 → 실제 경계는 `00:00:00`일 수 있다.

**따라서 `fire_at`과 `date_offset_days`를 반드시 설정값으로 노출**하고, 코드에 시각을 하드코딩하지
말 것. 첫 운영 며칠간 로그로 실제 열리는 시각을 관측해 조정할 수 있어야 한다.

## 7. Notion 기록

성공/실패 결과를 Notion 데이터베이스에 행으로 남긴다. **알림은 만들지 않는다.**

### 7.1 인증 및 사전 조건

- 사용자가 Notion 내부 통합(integration)을 만들고 **대상 데이터베이스에 그 통합을 연결**해 두었다.
  (Notion에서 DB → ⋯ → 연결 → 통합 추가). 연결이 없으면 API가 `object_not_found`를 반환한다.
- 공통 헤더:
  ```
  Authorization: Bearer <notion.token>
  Notion-Version: 2022-06-28
  Content-Type: application/json
  ```
- `database_id`는 32자리 hex다. 설정에 URL을 붙여넣어도 되게 **하이픈 제거 후 32자리 hex를
  정규식으로 추출**하는 정규화 함수를 둔다: `[0-9a-fA-F]{32}`.

### 7.2 스키마 조회 → 속성 이름 매칭

DB의 컬럼 구성은 사용자가 바꿀 수 있으므로 **하드코딩하지 않는다.**

```
GET https://api.notion.com/v1/databases/{database_id}
```

응답의 `properties` 객체(키 = 속성 이름, 값에 `type`)를 읽어, **속성 이름 패턴으로 역할을 매칭**한다.
아래 규칙은 기존 확장과 동일하게 유지해야 한다(같은 DB에 사람이 손으로 넣는 행과 포맷을 일치시키기 위함).

| 판정 순서 | 이름 정규식 | 채울 값 | 예시 |
|---|---|---|---|
| 1 | `현황` | 사용 현황 (§7.3) | `• 주간 정기 회의 12:00~16:00` |
| 2 | `회의실\|장소` | 회의실 표기 (§7.4) | `현승 4A` |
| 3 | `시간` (type ≠ date) | 예약시간 텍스트 | `12:00~16:00` |
| 4 | `예약자\|담당` | 담당자명 | `장초희` |
| — | type = `date` 중 `예약\|날짜\|일자\|date` 우선, 없으면 첫 date 속성 | 예약 날짜 | `2026-08-25` |
| — | type = `title` | 제목 | 회의명 |

**판정은 위 순서대로** 하는 것이 중요하다. `회의실 사용 현황`이라는 이름에는 "회의실"도 포함되므로
`현황`을 먼저 검사해야 오분류되지 않는다.

날짜 속성에는 **시간을 넣지 않는다** (`{"date":{"start":"2026-08-25"}}`). 시간 정보는 3번의
텍스트 속성으로 표현한다.

**title 속성 이름이 `회의실`/`장소` 인 경우** — 실제 운영 중인 `회의실 예약 현황` DB가 이 모양이다.
2번(회의실 표기)을 담을 다른 속성이 없으므로, 제목 칸이 회의실 역할을 맡는다: 제목에 `현승 5A` 가
들어가고 회의명은 1번(사용 현황)의 `• {회의명} {시작}~{종료}` 줄에만 남는다. 그 DB에 사람이 손으로
넣어 둔 행들이 정확히 그렇게 쓰여 있어서, 포맷을 맞추려면 이래야 한다. title 이름이 회의실과 무관하면
(예: `이름`) 종전대로 제목 = 회의명이다.

**`예약자` 가 `people` 타입인 경우** — people 속성에는 이름 문자열을 넣을 수 없고 사용자 id 가 필요하다.
이름 → id 를 세 군데에서 차례로 찾고, 찾는 즉시 멈춘다: ① `GET /users/me` 의 토큰 소유자,
② `GET /users` 목록(내부 통합 토큰은 *Personal access tokens cannot list users* 로 막힌다),
③ 그 DB에 이미 쌓인 행들의 people 값. 끝내 못 찾으면 그 속성만 비우고 기록은 그대로 진행한다.

### 7.3 사용 현황 포맷

```
• {회의명} {시작}~{종료}
```

- 불릿은 **`•` (U+2022)** 이며 하이픈이 아니다.
- 시간은 `HH:MM~HH:MM`, **종료시각은 사람이 읽는 실제 종료시각**(= 폼의 `wr_5`와 동일한 배타적 값).
  예: 12:00 시작, 8슬롯 → `• 주간 정기 회의 12:00~16:00`
- 여러 줄이 될 수 있으므로 rich_text로 저장하며 줄바꿈은 `\n`.

### 7.4 회의실 표기 포맷

`{빌딩 짧은이름} {층숫자}{호실 알파벳}` → 예: `현승 4A`

규칙:

1. 빌딩: 조회 응답의 "○○빌딩 N층" 문자열에서 `빌딩` 앞 토큰 (`현승빌딩 4층` → `현승`).
2. 층: 같은 문자열의 숫자 (`4`).
3. 호실 알파벳: **회의실명 문자열에서 처음 나오는 `A`~`D` (대소문자 무시, 대문자로 정규화)**.
   - `회의실 A` → `A`
   - `8인 회의실-1(회의실B)` → `B`
   - **알파벳이 하나도 없으면 무조건 `A`** (예: `4인 회의실-2` → `A`, `교육장` → `A`)

### 7.5 행 생성

```
POST https://api.notion.com/v1/pages

{
  "parent": { "database_id": "<32자리 hex>" },
  "properties": {
    "<title 속성명>":     { "title":     [ { "text": { "content": "주간 정기 회의" } } ] },
    "<현황 속성명>":      { "rich_text": [ { "text": { "content": "• 주간 정기 회의 12:00~16:00" } } ] },
    "<회의실 속성명>":    { "rich_text": [ { "text": { "content": "현승 4A" } } ] },
    "<예약시간 속성명>":  { "rich_text": [ { "text": { "content": "12:00~16:00" } } ] },
    "<예약자 속성명>":    { "rich_text": [ { "text": { "content": "장초희" } } ] },
    "<날짜 속성명>":      { "date":      { "start": "2026-08-25" } }
  }
}
```

타입별 페이로드 형태(속성 타입이 `rich_text`가 아닐 수도 있으므로 스키마의 `type`에 맞춰 생성):

| type | 페이로드 |
|---|---|
| `title` | `{"title":[{"text":{"content":"..."}}]}` |
| `rich_text` | `{"rich_text":[{"text":{"content":"..."}}]}` |
| `select` | `{"select":{"name":"..."}}` — 값이 없으면 `null` |
| `status` | `{"status":{"name":"..."}}` |
| `date` | `{"date":{"start":"YYYY-MM-DD"}}` |
| `number` | `{"number":123}` |
| `checkbox` | `{"checkbox":true}` |
| 그 외(`people`/`relation`/`rollup`/`formula`/`files`) | **전송하지 않는다** |

### 7.6 멱등성 (중복 기록/중복 예약 방지)

워밍업 단계에서 다음을 조회한다.

```
POST https://api.notion.com/v1/databases/{database_id}/query

{
  "page_size": 100,
  "filter": { "and": [
    { "property": "<날짜 속성명>", "date": { "on_or_after": "2026-08-25" } },
    { "property": "<날짜 속성명>", "date": { "before":      "2026-08-26" } }
  ]}
}
```

- 대상 날짜의 행이 **이미 존재하고 회의실 표기가 대상과 같으면** → 이미 처리된 것으로 보고
  **예약을 시도하지 않고 종료**한다(하루 2건 쿼터 낭비 방지).
- 이 판정은 보조 수단이다. 확실한 판정은 §3.6의 사이트 재조회다.

### 7.7 실패 시 기록

예약이 최종 실패해도 **로그에는 반드시 남기고**, Notion에는 설정에 따라 남긴다.

- `notion.record_failure: false` (기본): Notion에 아무것도 쓰지 않는다.
  DB는 "실제 예약 현황" 용도이므로 실패 행이 섞이면 오히려 방해가 된다.
- `true`인 경우: 회의명 앞에 `[실패]`를 붙이고 사용 현황에 실패 사유를 기록한다.

Notion 기록이 실패해도(토큰 만료, 연결 해제 등) **예약 성공 자체는 성공으로 처리**하고,
로그에 별도 에러를 남긴다. Notion 실패가 종료 코드를 오염시키지 않게 한다.

## 11. dry-run 및 최초 검증 절차 (필수)

`write_update.php`의 응답 형태가 **[미확인]**이므로, 아래 순서를 반드시 지킨다.
12시에 처음 돌려보면 디버깅 기회가 하루 한 번뿐이다.

**1단계 — dry-run으로 페이로드 확인**

`runtime.dry_run: true`로 실행한다. 최종 POST만 생략하고 다음을 출력한다.

- 로그인 성공 여부, 확보한 `uid` 목록
- 조회로 검증한 `room_id`/`building`/`floor` 일치 여부
- **전송 예정 폼 필드 전체(키=값)** — 특히 `wr_4`, `wr_5`, `wr_8`, `wr_3`
- Notion 속성 매칭 결과(어떤 속성에 어떤 값을 넣을지)

여기서 `wr_5 = wr_4 + slots×30분` 인지 눈으로 확인한다(§3.5 함정).

**2단계 — 경쟁 없는 시간에 실제 1회 예약**

`fire_at`을 지금 시각 몇 분 뒤로, `dry_run: false`로 두고 **실제로 한 번 예약을 성공시킨다.**
이때 응답 본문 전체를 저장해서(`log_level: debug`) 성공 응답의 형태를 확정하고, §3.6의
1차 판정 로직(alert 패턴 등)을 그 실측값에 맞춰 고정한다.

예약이 실제로 잡혔는지는 사이트를 브라우저로 열어 눈으로도 확인한다. 확인 후 그 예약은 취소한다.

**3단계 — 실패 응답도 한 번 관측**

이미 예약된 시간대로 일부러 POST 해서 **실패 응답 형태**를 확보한다. 성공/실패를 구분하는
판정이 실측 2종에 근거하게 된다.

**4단계 — cron 등록**

`fire_at`을 운영값으로 되돌리고 cron에 올린다. 첫 며칠은 로그를 확인해
발사 오프셋(50ms)과 `fire_at` 자체(§6.4)를 조정한다.

## 12. 에러 처리 매트릭스

| 상황 | 감지 방법 | 처리 |
|---|---|---|
| 로그인 실패 | 예약 페이지에 `uid` 없음 | 즉시 종료(코드 2). **재시도 금지** |
| `uid` 파싱 실패 | 정규식/셀렉터 불일치 | 종료(코드 4). 사이트 구조 변경 의심 |
| 조회 응답 행 0개 | `tr[data-wr8]` 개수 0 | 코드 4. 단, 7일 창 밖 날짜일 수 있으니 날짜 로그 확인 |
| `room_id` 불일치 | §5.0 검증 | 조회 응답 값으로 덮어쓰고 경고 로그 |
| 시간 겹침 / 이미 예약됨 | 응답 alert 또는 재조회 결과 | 다음 대상 → 폴백 → 실패(코드 3) |
| 하루 2건 초과 | 응답 alert | 재시도 무의미. 즉시 종료(코드 3) + 로그 명시 |
| `uid` 중복 거부 | 응답 alert | 풀에서 새 uid로 재시도. 풀 소진 시 페이지 재GET |
| 4시간 초과 | 설정 검증(§5.0) | 실행 전 차단(코드 1) |
| 7일 창 초과 | 조회 결과 비어있음 / alert | `date_offset_days` 재확인 필요. 코드 3 + 명시 로그 |
| 네트워크 타임아웃 | `http.Client.Timeout` | 재시도 루프 내에서 1회로 계산 |
| 서버 시계 오차 1초 이상 | `Date` 헤더 비교 | 경고 로그. 실행은 계속(NTP 점검 권고) |
| Notion 토큰 만료/연결 해제 | 401 / `object_not_found` | 예약 성공은 유지, 코드 5로 종료 + 로그 |
| Notion 속성 매칭 실패 | 해당 이름 정규식에 걸리는 속성 없음 | 그 속성만 생략하고 나머지 기록. 경고 로그 |

## 13. 완료 조건 (수락 기준)

1. `-config` 플래그로 설정 파일을 받아 동작하고, 설정 검증 실패 시 명확한 메시지와 코드 1로 종료한다.
2. `dry_run: true`에서 §11의 1단계 출력이 모두 나오며, **네트워크에 쓰기 요청을 전혀 보내지 않는다**
   (읽기 요청인 로그인/조회는 허용).
3. `wr_5 = wr_4 + duration_slots × 30분` 이 단위 테스트로 검증되어 있다.
   최소 케이스: `("12:00", 8) → "16:00"`, `("09:00", 1) → "09:30"`, `("20:30", 1) → "21:00"`.
4. 회의실 표기 함수에 단위 테스트가 있다.
   `("현승빌딩 4층","회의실 A") → "현승 4A"`, `("현승빌딩 4층","소회의실") → "현승 4A"`,
   `("해성빌딩 7층","회의실 B") → "해성 7B"`, `("회성빌딩 4층","8인 회의실-1(회의실B)") → "회성 4B"`,
   `("회성빌딩 6층","8인 회의실-2") → "회성 6A"`.
5. tbody 파싱 함수에 단위 테스트가 있다. **숨겨진 21:00 센티널 셀이 기예약 현황에 포함되지 않고,
   시간 셀이 정확히 24개로 인식**되어야 한다. (§부록 A의 샘플을 픽스처로 사용)
6. 슬롯 매칭 함수에 단위 테스트가 있다(연속 available 계산, 시작 윈도우 경계, 우선순위).
7. 실제 발사 시각과 목표 시각의 차이가 로그에 기록되며, 통상 **±20ms 이내**다.
8. 성공 시 Notion에 행이 1개 생성되고, `현황`/`회의실`/`예약시간`/`예약자`/`날짜` 값이 §7 포맷과 일치한다.
9. 같은 날 두 번 실행하면 두 번째는 멱등성 판정으로 예약을 시도하지 않고 코드 0으로 종료한다.
10. 재시도 총 요청 수가 설정 상한을 넘지 않는다(로그로 확인 가능).
11. 로그에 비밀번호/토큰이 어떤 레벨에서도 출력되지 않는다.
12. `CGO_ENABLED=0 GOOS=linux` 정적 빌드가 되고, 서버에서 추가 설치 없이 실행된다.

## 부록 A. 조회 응답 샘플 (테스트 픽스처)

`POST /ajax_common.php` (`std=location_select_new`, `wr_2=3`, `wr_3=2026.05.26`, `wr_4=회의공간`)
응답의 실제 일부다. 중간 시간 셀은 `...`로 줄였으나 **실제 픽스처는 24칸을 모두 채워야 한다.**

 <td class="selected tooltip2" data-time="10:30" idx="3" title="[앰버로드]앰버로드 과제회의" share_id="130785" data-toggle="tooltip" data-placement="top"></td>

- `available` 셀의 `title`은 시각 문자열이고, `selected` 셀의 `title`은 **회의명**이다.
- 마지막 셀은 `display:none` 센티널이다.
