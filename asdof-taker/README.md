# asdof-taker

jointips 회의실 **자동 예약 서비스**. 상주 Go 데몬 하나가 두 가지를 한다.

1. 정해진 시각에 **밀리초 정밀도로** 예약을 신청한다 (내부 스케줄러 — cron 불필요).
2. 그 설정을 관리하는 **웹 UI** 를 서빙한다 — <https://taker.asdof.xyz>

구현 근거는 [`자동 예약 기능.md`](자동%20예약%20기능.md) 명세다. 문서의 절 번호(§)를 코드 주석에 달아 두었다.

---

## 왜 상주 데몬인가

명세는 cron 기동을 전제했지만, 설정을 웹에서 바꿔야 하므로 상주 프로세스가 필요했다.
어차피 초 단위 정밀도는 프로그램이 직접 맞춰야 하니(§6.1) cron 은 없어도 된다.
RSS 는 10~20MB 수준이라 1GB 서버에도 부담이 없다.

## 자격증명 취급

웹에서 입력한 jointips 비밀번호와 Notion 토큰은

- **AES-256-GCM 으로 암호화**해서 `/var/lib/asdof-taker/config.json` (0600) 에 저장하고,
- 키는 같은 디렉터리의 `secret.key` (0600, 최초 기동 시 자동 생성) 에서 읽으며,
- **API 응답으로 절대 돌아 나오지 않는다** — "설정됨/미설정" 플래그만 나간다,
- **어떤 로그에도 남지 않는다** (`config.Mask` 를 거친다).

관리 페이지 자체는 관리자 비밀번호(PBKDF2-SHA256, 20만 회)로 잠겨 있고,
연속 실패 시 IP 별로 지수 백오프가 걸린다. 비밀번호를 바꾸면 다른 기기의 세션이 전부 끊긴다.

`ADMIN_PASSWORD` 는 **최초 1회 부트스트랩 값**이다. 이미 비밀번호가 있으면 무시하므로,
화면에서 바꾼 비밀번호가 재시작 때 되돌아가지 않는다.
잊어버렸다면 서버에서 `ADMIN_PASSWORD_RESET=1` 과 함께 재시작한다:

```bash
sudo systemctl edit --full asdof-taker   # 또는 /etc/asdof-taker.env 에 두 줄을 넣고
sudo systemctl restart asdof-taker       # 재설정 후 그 줄은 지운다
```

`TAKER_SECRET_KEY` 환경변수를 주면 키 파일 대신 그 값을 쓴다(키 순환용).

## 구조

```
main.go                     기동: vault → store → runner → scheduler → web
internal/config/            설정 타입·검증·원자적 저장 / vault.go 는 암호화·비밀번호 해시
internal/jointips/          사이트 프로토콜 (JSON REST — §0)
  client.go                 로그인(Bearer), 건물·공간·슬롯 조회, 신청, 내 예약
  rows.go                   슬롯 JSON → 현황 격자 조립
  match.go                  폴백 슬롯 탐색 (§5.2)
  format.go                 slotTimes 생성·회의실 표기 (§0.3, §7.4)
internal/notion/            스키마 매칭·행 생성·멱등성 질의 (§7)
internal/runner/
  runner.go                 워밍업 → 정밀 대기 → 발사 → 재시도 → 검증 → 기록
  scheduler.go              다음 발사 시각 계산 및 대기
internal/web/               관리 UI(HTML embed) + JSON API + 세션 인증
  catalog.go                건물·공간 목록을 사이트에서 받아 10분 캐시
```

### 명세의 함정들이 코드 어디에 있나

| 함정 | 위치 |
|---|---|
| `www.` 는 301 → POST 가 GET 이 돼 로그인 실패 (§0.1) | `config.CanonicalBaseURL` + `Migrate` |
| `slotTimes` 는 연속이어야 함 (§0.3) | `jointips.SlotTimes` — 테스트로 고정 |
| `MY_CONFLICT` 는 **선택 가능** (§0.2) | `Slot.Free` — `UNAVAILABLE` 만 막는다 |
| 운영 요일(토·일 휴무) (§0.4) | 발사 전 `BookableDays` 로 차단 |
| `reserveStatus≠Y` 공간은 신청 불가 (§0.4) | `Space.Bookable` → `Row.Bookable` |
| 한도 메시지 vs 자리 선점 (§0.5) | `isLimitMessage` — `"이미"` 로 가르면 안 됨 |
| 성공의 최종 근거는 내 예약 목록 (§0.5) | `verifyBooked` |
| 1회 3시간 · 1일 5시간 **(계정별)** (§0.4) | `config.MaxSlots` / `MaxDailySlots` / `MaxCount` |
| 예약 창 오늘~+7일 — **API 로 확인 불가** (§0.4) | `runner.checkWindow` — 사이트 시계로 계산 |
| 같은 층 다른 공간이 같은 라벨로 뭉개짐 | `RoomLabel` — 호실 글자 없으면 이름 그대로 |

## 배포

```bash
ADMIN_PASSWORD=... ./deploy.sh --nginx   # 최초: vhost + Let's Encrypt 까지
./deploy.sh                              # 이후: 코드/화면 갱신
```

- `127.0.0.1:8780` 에만 listen 한다. 외부 포트를 열지 않는다.
- systemd `asdof-taker` (www-data, `MemoryMax=128M`, `StateDirectory` 0700).
- `TZ=Asia/Seoul` 을 유닛에 박아 둔다. **서버 NTP 가 켜져 있어야 한다** (§6.2).
- `--nginx` 재실행 시 certbot 이 손댄 vhost 는 덮어쓰지 않는다(HTTPS 유실 방지).

## 첫 운영 절차 (§11)

1. **계정·보안** 탭에서 jointips 아이디(이메일)/비밀번호 저장 → **로그인 테스트**.
2. **예약 설정** 탭에서 회의명·담당자·이용목적과 대상 회의실/시간 지정.
   («현황 조회» 탭에서 빈 칸을 클릭해 추가해도 된다.)
   회의실 목록은 사이트에서 받아 온다 — 바뀌었으면 **스케줄** 탭의
   «회의실 목록 — 사이트에서 새로 받기»를 누른다.
3. **드라이런 실행** → 로그에서 `spaceCd` / `date` / `slots` 를 눈으로 확인.
   특히 `slots` 가 30분 간격으로 **연속**인지 본다.
4. 경쟁 없는 시간에 **지금 예약 시도**를 한 번 눌러 실제 성공 응답을 관측한다.
   (사이트에서 눈으로도 확인하고, 확인 후 그 예약은 취소한다.)
5. **스케줄** 탭에서 발사 시각·요일을 정하고 자동 예약을 켠다.
   처음 며칠은 실행 기록의 **발사 오차(ms)** 를 보고 `fire_at` 을 조정한다.

> **`fire_at` 기본값은 `00:00:01.000` 이다.** 예약 창은 자정에 롤링하는데, 그 자정은
> **jointips 서버의 시계** 기준이다. 개편 전 서버는 실제보다 40분 가까이 느려서 `00:40:01` 로
> 미뤄 뒀지만, 새 서버는 ±0.1초 수준으로 정확해 자정 직후로 되돌렸다.
>
> 앱은 매 스케줄 주기마다 `Date` 헤더로 이 오차를 재서 **화면 하단 각주에 보여준다**(자동으로
> 환산하지는 않는다 — 사람이 보고 정한다). 각주의 숫자가 다시 커지면 그만큼 앞당겨야 한다.
>
> `date_offset_days` 는 **0~7** 이고 기본값은 **7** 이다. 창이 `오늘 ~ 오늘+7일`(양끝 포함)이라
> 막 열린 날짜가 +7일이다(개편 전에는 `< 오늘+7` 이라 +6이었다). 요일도 이때 딱 맞는다 —
> +7이면 실행 요일과 예약 요일이 같아서, 월~금 실행이 월~금 예약이 된다.

## 계정 여러 개 — 한도는 계정별이다

사이트 한도(**하루 2회 · 총 5시간**, 1회 최대 3시간)는 **계정(아이디)별**이다.
그래서 계정을 N개 두면 하루 상한이 `2N`건으로 늘어난다(`config.MaxCount`).

- 워밍업에서 **모든 계정을 미리 로그인**해 둔다. 한 계정이 막힌 뒤에 로그인하면
  발사 직후의 가장 비싼 순간에 왕복이 하나 더 붙는다.
- 앞 계정부터 한도까지 쓰고 다음으로 넘어간다(`pickSeat`). 한도 메시지를 받으면
  그 계정만 접고 **같은 자리를 다음 계정으로 다시 노린다**.
- 계정 하나가 잠겨도 나머지로 계속 간다. 전부 실패해야 실행이 실패다.
- 같은 아이디를 두 번 넣는 건 막는다 — 좌석이 둘로 보이지만 한도는 하나라
  잡을 수 있는 건수를 부풀려 계산하게 된다.
- Notion 의 예약자는 그 건을 잡은 **계정의 회원 이름**으로 들어간다.

## 스케줄 — 요일 반복 / 지정 스케줄

| 모드 | 동작 |
|---|---|
| `weekly` | 고른 요일마다 반복 |
| `dates` | **캘린더에서 찍은 날짜에만** 실행 (`schedule.entries`) |

**둘은 배타적이다** — `schedule.mode` 하나로 갈리므로 한쪽을 켜면 다른 쪽은 돌지 않는다.

요일을 **하나도 안 고르면 실행하지 않는다**. 예전에는 빈 목록을 '매일'로 봤는데,
요일 반복을 그만두려고 전부 끈 사람이 오히려 매일 돌게 되는 함정이었다.
매일 돌리려면 7개를 다 고른다.

지정 스케줄의 캘린더는 **실행일**을 고르는 자리다. 칸 아래 작은 글씨가 그날 실제로
잡히는 **대상 날짜**다. 대상 날짜가 사이트 휴무일(토·일)인 칸은 고를 수 없다 —
골라 봐야 그날은 아무것도 안 잡힌다.

### 예약별 설정 (`schedule.entries`)

**항목 하나 = 회의실 한 개를 잡는 예약 한 건**이다(`config.ScheduleEntry` → `runner.job`).
`targets` 는 그 하나를 잡기 위한 **후보 목록**이고, 위에서부터 돌려 가며 시도해
하나가 확인되면 그 건은 끝난다 — 여러 개를 잡는 게 아니다.
후보가 다 막히면 `fallback` 이 같은 건물에서 빈 자리를 찾아 후보를 보충한다.

**같은 실행일에 여러 건을 넣을 수 있다.** 그날 예약 두 개가 필요하면 항목을 두 개 만든다.
한 번 발사로 그날의 건들이 순서대로 나간다(`Schedule.EntriesOn`).

| 필드 | 비우면 |
|---|---|
| `target_date` 대상 날짜 | 실행일 + `booking.date_offset_days` |
| `subject` 회의명 | `booking.subject` |
| `manager` 담당자명 | 계정 회원명 → `booking.manager` |
| `purpose_cd` 이용목적 | `booking.purpose_cd` |
| `account_id` 예약자 | 등록된 계정을 앞에서부터 (자동) |
| `targets` 회의실 후보 | `booking.targets` |
| `fallback` 폴백 | `booking.fallback` (`nil` 일 때만. 끄려면 `enabled:false` 로 넣는다) |

**비운 칸은 「예약 설정」을 그대로 상속한다** — 날짜만 찍어 둔 항목은 예전과 똑같이 동작한다.
「예약 설정」 탭은 지정 스케줄을 쓸 때 **기본값** 역할을 한다.

건마다 대상 날짜가 다를 수 있어서 예약 창 점검·휴무 요일 점검·현황 조회·Notion 멱등성은
**날짜별로** 돈다. 한 날짜가 막혀도 다른 날짜의 건은 그대로 간다.

두 가지는 저장 시점에 막는다: `target_date` 가 실행일 기준 0~7일 밖(사이트 예약 창),
그리고 없는 계정을 예약자로 지목하는 것. 예약자를 못박은 항목은 **그 계정만** 로그인한다 —
다른 계정으로 잡히면 그 사람 이름으로 예약이 걸려 버린다.

카드는 기본적으로 **접혀 있고** 한 줄 요약(대상 날짜 · 회의명 · 회의실 · 예약자 · 폴백)만
보인다. 눌러서 펼치면 편집할 수 있다. 새로 만든 건 바로 채워 넣도록 펼친 채로 나온다.
펼침 상태는 `EXPANDED` 가 들고 있다 — 카드는 편집할 때마다 다시 그려지므로 DOM 밖에 둬야 한다.

항목마다 «드라이런» 버튼이 있어 그 설정 그대로 한 번 돌려 볼 수 있다
(`POST /api/run {entry_id}`). `{date}` 를 주면 그날의 건 전부를 돌린다.

같은 날·같은 공간·같은 시각을 두 건이 함께 노리면 뒤엣것은 반드시 실패하므로
저장 시점에 막는다. 실행 중에도 이미 잡은 자리는 다음 건의 후보에서 빠진다.

날짜가 모두 지나면 스케줄러가 "지정한 실행 날짜가 모두 지났습니다"로 멈추고 화면에
그 이유를 띄운다. 조용히 안 돌면 안 잡힌 걸 모른다.

## 예약 길이 — 1회 3시간 제한

**1회는 최대 3시간(6칸)**이라 4시간짜리는 애초에 불가능하다 — 저장 시점에 걸러 준다.

예약 건 사이에는 `booking.gap_seconds`(기본 2초)만큼 기다린다. 개편 전 그누보드의
도배 방지(`cf_delay_sec` 30초)는 사라져서 짧게 둬도 되지만, 같은 계정으로 연달아 쏘는 것을
굳이 서두를 이유가 없어 남겨 뒀다. 재시도 예산(`retry.max_duration_s` / `max_attempts`)은
**예약 건마다 새로** 부여된다 — 대기가 앞 건의 예산을 잡아먹으면 두 번째를 아예 못 쏘기 때문이다.

거절 사유가 **계정 한도**면 오늘 안에 풀리지 않으므로 즉시 멈추고, **자리 선점**이면 재시도한다.

## 테스트

```bash
go test ./...          # 파서·매칭·포맷·검증·인증
go test -race ./...
```

`internal/runner/runner_test.go` 는 jointips 의 새 JSON API 를 흉내 낸 가짜 서버를 띄워
로그인 → 발사 → 재시도 → 내 예약 목록 검증 → 폴백 → 발사 타이밍까지 통째로 돌린다.
휴무 요일 차단, 한도 메시지 즉시 중단, 신청 200 만으로는 성공으로 치지 않는 것까지 고정해 뒀다.

`cmd/probe` 는 서버에서 실제 자격증명으로 API 를 두드려 보는 조사 도구다
(`-dryrun` 은 Runner 를 드라이런으로 돌린다 — 반드시 상태 디렉터리 **사본**을 대상으로).
