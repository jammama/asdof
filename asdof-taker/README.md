# asdof-taker

jointips 회의실 **자동 예약 서비스**. 상주 Go 데몬 하나가 두 가지를 한다.

1. 정해진 시각에 **밀리초 정밀도로** 예약을 신청한다 (내부 스케줄러 — cron 불필요).
2. 그 설정을 관리하는 **웹 UI** 를 서빙한다 — <https://taker.asdof.xyz>

구현 근거는 [`자동 예약 기능.md`](자동%20예약%20기능.md) 명세다. 문서의 절 번호(§)를 코드 주석에 달아 두었다.

---

## 왜 상주 데몬인가

명세는 cron 기동을 전제했지만, 설정을 웹에서 바꿔야 하므로 상주 프로세스가 필요했다.
어차피 초 단위 정밀도는 프로그램이 직접 맞춰야 하니(§6.1) cron 은 없어도 된다.
RSS 는 10~20MB 수준이라 1GB 서버에도 부담이 없다.

## 자격증명 취급

웹에서 입력한 jointips 비밀번호와 Notion 토큰은

- **AES-256-GCM 으로 암호화**해서 `/var/lib/asdof-taker/config.json` (0600) 에 저장하고,
- 키는 같은 디렉터리의 `secret.key` (0600, 최초 기동 시 자동 생성) 에서 읽으며,
- **API 응답으로 절대 돌아 나오지 않는다** — "설정됨/미설정" 플래그만 나간다,
- **어떤 로그에도 남지 않는다** (`config.Mask` 를 거친다).

관리 페이지 자체는 관리자 비밀번호(PBKDF2-SHA256, 20만 회)로 잠겨 있고,
연속 실패 시 IP 별로 지수 백오프가 걸린다. 비밀번호를 바꾸면 다른 기기의 세션이 전부 끊긴다.

`ADMIN_PASSWORD` 는 **최초 1회 부트스트랩 값**이다. 이미 비밀번호가 있으면 무시하므로,
화면에서 바꾼 비밀번호가 재시작 때 되돌아가지 않는다.
잊어버렸다면 서버에서 `ADMIN_PASSWORD_RESET=1` 과 함께 재시작한다:

```bash
sudo systemctl edit --full asdof-taker   # 또는 /etc/asdof-taker.env 에 두 줄을 넣고
sudo systemctl restart asdof-taker       # 재설정 후 그 줄은 지운다
```

`TAKER_SECRET_KEY` 환경변수를 주면 키 파일 대신 그 값을 쓴다(키 순환용).

## 구조

```
main.go                     기동: vault → store → runner → scheduler → web
internal/config/            설정 타입·검증·원자적 저장 / vault.go 는 암호화·비밀번호 해시
internal/jointips/          사이트 프로토콜
  client.go                 로그인, uid 풀, 조회, 신청 POST, 겹침 확인
  parse.go                  tbody 조각 파싱 (센티널·rowspan 함정 처리)
  match.go                  폴백 슬롯 탐색 (§5.2)
  format.go                 wr_5 계산·회의실 표기 (§3.5, §7.4)
  codes.go                  빌딩/층/회의실 코드표 (UI 드롭다운용)
internal/notion/            스키마 매칭·행 생성·멱등성 질의 (§7)
internal/runner/
  runner.go                 워밍업 → 정밀 대기 → 발사 → 재시도 → 검증 → 기록
  scheduler.go              다음 발사 시각 계산 및 대기
internal/web/               관리 UI(HTML embed) + JSON API + 세션 인증
```

### 명세의 함정들이 코드 어디에 있나

| 함정 | 위치 |
|---|---|
| `wr_5` 는 **배타적** 종료시각 (§3.5) | `jointips.FormEndTime` — 테스트로 고정 |
| `dup_time` 의 `wr_5` 는 의미가 다름 (§3.7) | `jointips.DupEndTime` |
| `dup_time` 응답 `"OK"` = 예약 **불가** (§3.7) | `Client.DupTime` |
| `display:none` 21:00 센티널 셀 (§3.4) | `ParseRows` — 격자에서 제외, 테스트로 고정 |
| rowspan 으로 생략된 빌딩/층 셀 (§3.4) | `ParseRows` — 이전 행에서 물려받음 |
| HTTP 200 이어도 실패일 수 있음 (§3.0) | `alertMessage` + 재조회 검증 |
| 성공의 최종 근거는 재조회 (§3.6) | `verifyBooked` |
| 7일 창 (§3.9) | 빈 조회 응답을 감지해 경고 |
| uid 재사용 거부 (§3.2) | uid 풀 — 시도마다 새 값 |

## 배포

```bash
ADMIN_PASSWORD=... ./deploy.sh --nginx   # 최초: vhost + Let's Encrypt 까지
./deploy.sh                              # 이후: 코드/화면 갱신
```

- `127.0.0.1:8780` 에만 listen 한다. 외부 포트를 열지 않는다.
- systemd `asdof-taker` (www-data, `MemoryMax=128M`, `StateDirectory` 0700).
- `TZ=Asia/Seoul` 을 유닛에 박아 둔다. **서버 NTP 가 켜져 있어야 한다** (§6.2).
- `--nginx` 재실행 시 certbot 이 손댄 vhost 는 덮어쓰지 않는다(HTTPS 유실 방지).

## 첫 운영 절차 (§11)

1. **계정·보안** 탭에서 jointips 아이디/비밀번호 저장 → **로그인 테스트**.
2. **예약 설정** 탭에서 회의명·담당자·연락처와 대상 회의실/시간 지정.
   («현황 조회» 탭에서 빈 칸을 클릭해 추가해도 된다.)
3. **드라이런 실행** → 로그에서 `wr_4` / `wr_5` / `wr_8` / `wr_3` 를 눈으로 확인.
   특히 `wr_5 = wr_4 + 슬롯수 × 30분` 인지 본다.
4. 경쟁 없는 시간에 **지금 예약 시도**를 한 번 눌러 실제 성공 응답을 관측한다.
   (사이트에서 눈으로도 확인하고, 확인 후 그 예약은 취소한다.)
5. **스케줄** 탭에서 발사 시각·요일을 정하고 자동 예약을 켠다.
   처음 며칠은 실행 기록의 **발사 오차(ms)** 를 보고 `fire_at` 을 조정한다.

> **`fire_at` 기본값은 `00:40:01.000` 이다.** 명세 §6.4 가 의심했던 대로 예약 창은 **자정에 롤링**한다.
> 정오가 아니다. 다만 그 자정은 **jointips 서버의 시계** 기준인데, 그 시계가 실제보다 **약 39분 느리다**(실측,
> 2026-08-25). 그래서 새 날짜가 실제로 열리는 시각은 우리 시계로 00:39 무렵이고, 여기에 여유를 얹은 값이다.
>
> 앱은 매 스케줄 주기마다 `Date` 헤더로 이 오차를 재서 **화면 하단 각주에 보여준다**(발사 시각을 자동으로
> 환산하지는 않는다 — 사람이 보고 정한다). jointips 가 시계를 고치면 각주의 숫자가 0에 가까워지므로,
> 그때 `fire_at` 을 `00:00:01` 근처로 되돌리면 된다.
>
> `date_offset_days` 는 **6** 이다. §3.9 의 창이 `오늘 <= 날짜 < 오늘+7` 이므로 막 열린 날짜가 +6일이다.

## 하루 2건 잡기 — 도배 방지 주의

사이트는 팀당 하루 2건까지 받지만, gnuboard 의 **도배 방지**(`cf_delay_sec`, 기본 30초)가
같은 계정의 연속 등록을 막는다:

```
너무 빠른 시간내에 게시물을 연속해서 올릴 수 없습니다.
```

그래서 첫 건을 잡은 뒤 곧바로 두 번째를 쏘면 무조건 튕긴다(2026-08-28 실운영에서 39번 헛방).
`booking.gap_seconds`(기본 35초)만큼 기다렸다가 다음 건을 신청하며, 재시도 예산
(`retry.max_duration_s` / `max_attempts`)은 **예약 건마다 새로** 부여된다 — 대기가 앞 건의
예산을 잡아먹으면 두 번째를 아예 못 쏘기 때문이다.

도배 방지에 걸리면 재시도가 아니라 대기로 대응하고(최대 3회, 그 뒤 포기), 확보한 건은 살린다.

## 테스트

```bash
go test ./...          # 파서·매칭·포맷·검증·인증
go test -race ./...
```

`internal/runner/runner_test.go` 는 jointips 를 흉내 낸 가짜 서버를 띄워
로그인 → 발사 → 재시도(새 uid) → 재조회 검증 → 폴백 → 발사 타이밍까지 통째로 돌린다.
실제 사이트의 `write_update.php` 성공 응답 형태는 **[미확인]** 이므로(§3.6),
1차 판정(alert 패턴)은 첫 실운영에서 관측한 값으로 고정해야 한다.
